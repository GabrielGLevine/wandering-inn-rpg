# Project Briefing — Wandering Inn RPG (for the incoming project lead)

You are taking over as lead on a Godot game project. You have broad latitude to change
architecture and design in service of the goal. This document is your orientation: the goal,
what actually exists today (told straight), the strategic decisions already made and *why*, the
ones still open, and how work gets done here. Read it once end-to-end before touching anything.

Everything factual here is cross-referenced to a canonical doc so you can verify rather than
trust me. Where I give an *opinion* or flag a *risk*, it's marked as such — you're free to
overrule any of it.

---

## 1. The Goal

Build a real, playable RPG set in the world of **The Wandering Inn** (a long-running web serial).
The defining fictional mechanic is its **[Class] and [Skill] system**: characters hold classes,
gain levels, and unlock named Skills — and level-ups happen when a character *sleeps*, not from
an XP bar (this is canon and has already shaped the design; see §4).

**Hard product constraint, repo-wide:** the player never sees raw stat numbers (STR/DEX/CON/etc.).
The Wandering Inn source material has no visible stat sheet. Player-facing UI shows only race,
class, level, Skills, HP/MP, and gear. This has been violated by accident before — guard it.

**Lore is not free-authored.** Canon (characters, Skills, classes, place names) comes from the
[Wandering Inn Wiki](https://wiki.wanderinginn.com/The_Wandering_Inn_Wiki). Treat it as source of
truth whenever content is written or reviewed.

- **v2 MVP** — character creation → meet Erin (innkeeper) → travel to Liscor → recruit Relc →

- **v3 "Defend the Inn" vertical slice** — extends the MVP into a complete small quest with real

**The current head-of-`main` game is a ~10-minute vertical slice.** It demonstrates that the
engine + progression layer can carry a real Wandering-Inn quest loop. It is *not* a large or deep
game yet, and the combat is the base engine's simple readiness-bar (ATB) system, unchanged.

## 3. Architecture in Two Minutes

Three Godot projects live in this repo — **only one is active**:

- **`wandering_inn_game_v2/`** ← the active game. Work here.
- `wandering_inn_game_v1/` — abandoned earlier attempt (built everything from scratch, incl. a
  *tactical-grid* combat system). Kept for reference/content mining only. See §4.
- `godot-open-rpg/` — the upstream GDQuest teaching demo v2 was cloned from. Gitignored, separate
  repo, clone-source only. Never commit into it.

v2 = **GDQuest's `godot-open-rpg` engine** (field movement w/ pathfinding, cutscene/trigger system,
Dialogic dialogue, ATB combat) **+ a Wandering Inn progression layer** bolted on under
`src/rpg/`. The engine is decoupled into a **field state** and a **combat state**, each with its
own signal-bus autoload; they talk only through those buses.

The progression layer's load-bearing pieces:
- `WIPlayerState` autoload — the run's character state + quest progress flags (`accomplishments`,
  `seen_hints`). `record_accomplishment(id)` is the single source of truth for progress.
- `WIClassCatalog` autoload — class/skill definitions.
- `PCBattlerBuilder` — the **player** battler is built *dynamically* at combat start from
  `WIPlayerState`; companions/enemies are static hand-authored `.tres`. Level-ups therefore never
  mutate a live battler — you sleep, your state changes, and the *next* fight builds you at the new
  level. This was a deliberate simplification (see §4).

Full architecture, file-by-file conventions, and the specific gotchas that have bitten us:
→ **`wandering_inn_game_v2/CLAUDE.md`** (and the root **`CLAUDE.md`** for repo-wide rules).

## 4. Key Decisions Already Made — and Why (all overrulable)

You have latitude to change these. Here's the reasoning so you can weigh what you'd break.

1. **Build on the GDQuest demo engine instead of from scratch.** v1 built its own field/dialogue/
   combat and stalled under the weight. v2 traded a from-scratch tactical system for a working,
   polished-but-simple ATB engine to get to *playable* fast. **The tension this creates (your call
   to resolve):** Wandering Inn's Skill system is large and positional/idiosyncratic; **67 of v1's
   78 skills were built for grid combat** and do not map cleanly onto ATB. The MVP deliberately
   punted on this. *My flagged risk:* if the long-term vision needs tactical/positional combat
   depth, the current ATB engine is the single biggest architectural bet to re-examine — v1's
   abandoned grid system is right here to mine, and this is exactly the kind of foundational call a
   new lead is best placed to make early, before content scales on top of the current assumption.

2. **Level up by sleeping, not by XP.** Canon-driven (a user lore correction during design). Nicely
   sidesteps mid-combat battler mutation: progression resolves at a "sleep" beat between fights,
   and `PCBattlerBuilder` just builds you fresh at the new level next fight. Simple and lore-true.

3. **Stats hidden from the player** (see §1). Non-negotiable *product* constraint, but *how* you
   surface progression (the current level-up toast is minimal) is open design space.

4. **`check_for_level_up()` is hardcoded for Fighter 1→2**, not a general leveling curve. Intentional
   YAGNI for the slice. Generalizing this is an obvious early task once you commit to breadth.

5. **All placeholder art.** No art pipeline exists. Sprites are reused GDQuest demo assets (Relc is
   a "gobot," props are misc. character sprites picked for visual distinctness, not theme). Whether/
   when to invest in real art is an open product decision.

Design specs and plans with full rationale live in `docs/superpowers/specs/` and
`docs/superpowers/plans/` (v2 MVP + v3 slice each have both).

## 5. Where the Bodies Are Buried (process risks — read this twice)

The single most important operational fact:

> **The agent tooling here cannot playtest.** There is no screenshot capture and no input
> injection. Automated checks are limited to: headless parse (`--quit`), running `SceneTree` test
> scripts, and capturing a boot log. **A feature can pass every test, parse clean, and still be
> completely broken or invisible to a player.** This has happened twice already:
>
> - The entire v3 quest chain was *dead* in real play — the Shield Spider victory never recorded the
>   accomplishment that gates everything downstream — yet every unit test passed (they called the
>   state method directly, masking the missing wiring). Caught only by the final whole-branch review.
> - The fortify-beat tutorial hint "worked" but used `print()`, so it only ever reached the Godot
>   console, never the player. The fortify props reused Relc's exact sprite, so they were
>   indistinguishable from an NPC. Both caught only by a human actually playing.

**Implication for how you run this project:** treat human-in-the-loop playtesting as the real QA
gate, not tests. Tests here should assert *wiring* (does the node reference the script that does the
real thing), not just that a method works in isolation. When you build anything player-facing, ask
"would a first-time player see this and know what it means," not "does the code path execute." This
lesson is baked into both `CLAUDE.md` files — but it's the thing most likely to burn you, so it's
here too.

Other known-open items are tracked in `HANDOFF.md` (the remaining v3 playtest past the fortify beat
has not been human-confirmed yet).

## 6. How Work Gets Done Here

- **Direct on `main`.** No long-lived branches or worktrees, by standing preference. Commit when a
  unit of work is verified.
- **Subagent-driven.** Implementation is delegated to lower-level agents. The established workflow
  is the Superpowers chain: `brainstorming` → `writing-plans` → `subagent-driven-development`
  (fresh implementer subagent per task, a spec+quality review after each, a broad whole-branch
  review at the end). The final whole-branch review is what caught the dead quest chain — **do not
  skip it.**
- **Godot-specific implementation** uses the **GodotPrompter** (`godot-prompter:*`) skills and its
  specialized agents (`godot-game-dev`, `godot-ui-designer`, `godot-code-reviewer`, etc.). The
  Superpowers workflow governs *process*; GodotPrompter governs *Godot patterns*. Use both.
- **Model discipline for subagents:** cheap/fast model for mechanical transcription tasks, mid-tier
  for prose-driven implementation and reviews, most capable for architecture and the final review.
  Always set the model explicitly on dispatch.
- **Verification cost tip (from the user):** prefer headless `godot` CLI checks over the Godot MCP
  tools for routine parse/test runs — MCP output stays resident in agent context and isn't dropped
  on compaction, so it's more token-expensive over a long session. Reserve MCP boot for cases that
  genuinely need a live scene-tree (e.g. runtime autoload resolution a `--script` run can't do).
- **`HANDOFF.md` is the handoff protocol.** Keep it current *as you go*, not just at session end —
  the user may switch agents (e.g. to Codex) at any point and needs it to reflect reality.
