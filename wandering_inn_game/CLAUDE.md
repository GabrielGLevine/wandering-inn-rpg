# CLAUDE.md

Guidance for Claude Code in `wandering_inn_game/` — active Wandering Inn RPG project (M0: agent-QA foundation + walking skeleton).

## What this is

Fresh Godot 4.7 project, QA-first: every feature must be agent-verifiable, no human playtest. See
`docs/superpowers/specs/2026-07-01-wandering-inn-v4-agent-qa-foundation-design.md`
for architecture rationale + north star (BG3-in-Wandering-Inn, team of 1, [Skills] usable outside combat).

**Product constraints (repo-wide, non-negotiable):** HP readouts + damage numbers player-visible (playtest decision, M2); raw STR/DEX/etc. stay forbidden. Lore canon from Wandering Inn Wiki, never invented.

## Architecture

Full mechanism detail, rollout narrative, design rationale for every system: `docs/ARCHITECTURE-HISTORY.md`. This section current-state-only, one short paragraph per live system.

- **Sim core (`src/core/wi_game.gd`)** — `WIGame`, pure `RefCounted` sim. PURITY RULE: no autoload/Node/scene-tree refs in sim code, ever; dependencies injected (config dicts, event-sink `Callable`, seed). Keeps sim headless-testable, mass-simulatable.
- **ObservableBus (autoload)** — single pipe for every player-visible / QA-relevant domain event (`emit_domain_event`, JSONL log + signal). Never `print()` anything player should see; UI nodes render from bus events, emit `ui_*_rendered` confirmations back onto bus.
- **Game (autoload)** — owns `WIGame` instance, wires event sink to bus, owns save/load file I/O.
- **Presentation (`src/world/world.gd`, `src/ui/message_layer.gd`, `src/world/main.tscn`)**
  — thin: forwards input to `Game.sim`, renders state from bus events. All UI built in code; content in `data/*.json`. `main.tscn` = only hand-authored root scene (`project.godot`'s `run/main_scene`) — `src/world/world.tscn` orphaned byte-identical duplicate, nothing references it. Render pipeline (M5): 1280×720 window, 320×180 world `SubViewport` scaled 4×, centered (fractional `canvas_items` stretch, not integer). Environment schema (M5 E3): maps use `floor_layers`, `walls.segments` (walls-v2 records; `WIGame.segment_cells` = single cell-expansion source shared by sim blocking + tests), `decor`, `scatter`. Field held-key movement (2026-07-05): held keys re-issue `move_player` on each move-tween `finished` signal, gated same as fresh press; collapses to 0 duration under QA/headless — unobservable to tests. Full detail: "Presentation" + "Demo feel + render pipeline (M5)" + "Environment schema (M5 E3)" blocks in `docs/ARCHITECTURE-HISTORY.md`.
- **Field hotbar (`src/ui/field_hotbar.gd`, Three Pillars P2)** — overworld twin of combat action bar; shows PC's known field-tagged skills (`Game.sim.known_skills()` filtered by `skills.json`'s `field: true`), hides during combat, reuses `WIHotbar` for render. Number keys route through `world.gd` existing movement/interact gate. **Tab-primed select (issue #58):** Tab arms/disarms the same pad-cursor seam `[`/`]`/LB/RB already drive (`world.gd`'s `_field_slot_index`) — primed, arrow left/right cycle the highlighted slot (wrapping) instead of moving the player, up/down are swallowed (no drift while aiming), confirm fires the highlighted slot and cancel disarms (both pre-existing branches), and a direct number-key press also disarms for one-shot consistency. Every selection change draws a small floating `[Skill Name]` label above the highlighted slot (`display_name` is already bracket-formatted) and emits `UI_FIELD_HOTBAR_SELECTION_RENDERED` (distinct from `UI_FIELD_HOTBAR_RENDERED`, which means "the slot list changed" — this one means "the highlight changed").
- **TestDriver (autoload, `qa/test_driver.gd`)** — inert unless `--qa-script=...` passed. Executes declarative JSON playtests: injects real input, waits for bus events (`payload_contains` subset match), screenshots, asserts on `Game.sim.snapshot()`, drives fights via `combat_autoplay`, writes `result.json`. Per-script routing/rationale: `docs/QA-SCRIPT-NOTES.md`; script list: canonical seed table below.
- **Combat (`WICombat`, `src/core/combat/wi_combat.gd`)** — pure per-encounter tactical sim: 12×8 grid, 4 AP/turn, precomputed initiative, seeded RNG, reaction hooks (riposte, momentum). Movement economy: `move_pool` (3 free steps/turn) spends before AP; `dash()` costs 1 AP for +3 pool. LoS = supercover raycast (symmetric, corner rule); line skills clip at first wall, hit everything in line (friendly fire real). MP: `max_mp = 8 + int/2`, granted only when combatant holds any `mp_cost` skill. **PC death = immediate defeat**, even with living ally (`_check_end` checks `pc.alive` first) — any future combat-data/sim change must re-check this failure mode; `defeat_ally_alive` = canonical proof. `WISkillEffects` = active-effect registry; `WICombatAI` = deterministic role AI (`melee`/`ranged`/`caster`/`inert` profiles — PC's own combatant config defaults to `melee`, so `combat_autoplay` never casts spell or fires line-skill refusal for player; see Gotchas). Presentation decomposed into components (M6.5): `combat_screen.gd` = only mode FSM + input dispatch; `board_renderer.gd`/`combat_view.gd`/`combat_playback.gd`/`combat_hud.gd`/
  `targeting_controller.gd` each own one concern — new presentation code goes in matching component, never back into `combat_screen`. Combat controls: arrows move active unit directly (move pool before AP), number keys = hotbar slots, Dash arms confirm gate (Enter/Esc), never fires instantly. Full detail: "Combat (M1)" / "Combat depth (M3)" / "Combat controls" / "Combat presentation components (M6.5)" blocks in `docs/ARCHITECTURE-HISTORY.md`.
  **Area terrain (GH#21, [Ice Floor]):** `WICombat.terrain` = `Vector2i cell -> {kind, expires_after_round, applies}` map, populated only by `WISkillEffects.resolve_active`'s `icy_floor` arm (Chebyshev-radius blast around TARGET's cell, walls/out-of-bounds excluded), purged in `_advance_turn` round-rollover branch. Standing on or stepping onto terrain cell applies its `applies` statuses via `_apply_terrain_status` (two call sites: `move_active`, `_start_turn`). **AI selects it since #90**: `combat_ai.gd`'s area_skill arm (`_act_area` in `_act_ranged`) casts icy_floor/blast_damage when the blast catches >=2 living enemies and zero allies — goblin_shaman carries it live; an enemy-cast zone is real. `ice_floor_loop` = player-cast canonical; `shaman_zone_loop` = the ENEMY-cast/area-arm canonical.
  **AoE blast damage (GH#71, [Flame Pillar]):** `blast_damage` effect type — instant damage sibling to `icy_floor`, sharing its exact area derivation (`WISkillEffects._radius_area`, renamed from `_icy_floor_area` when this task generalized it): Chebyshev-radius blast around the TARGET's cell, walls excluded, no new targeting mode (same enemy-cycling UI as `icy_floor`/`spell_damage`). Every living occupant of the area is hit regardless of side (friendly fire real, including the caster's own cell) via `_resolve_line_damage`'s multi-hit application shape — no terrain write, no status write, no expiry seam (contrast `icy_floor`, which glazes+slows for `duration_rounds`). First grant: fire_mage L11 `flame_pillar` (3 AP/5 MP, radius 1, range 3 — costs more than `flame_jet`'s 2 AP/4 MP single-line skill). No `icon` field (every fire-blast icon asset is already claimed by a shipped skill; degrades gracefully like the dozen other iconless skills, disclosed as an art-pass gap). **AI selects it since #90** (the same `combat_ai.gd` area_skill arm as `icy_floor`) — `rift_vermin_c` carries it live in the rift_vermin_leak/trapped_halls_snare rosters (both GATED bands re-verified). `flame_pillar_loop` = canonical proof.
  **Range+LoS attack seam (GH#70, [Archer]):** every combatant carries `weapon_range` (`WIKeys.WEAPON_RANGE`, defaults 1/melee; `wi_game.gd`'s `_build_player_combatant` threads it from the equipped weapon's items.json `range` field — PC-only today, no enemy carries a ranged weapon). `WICombat.in_weapon_range(attacker, target)` is the ONE gate both `attack()` and `skill_effects.gd`'s `damage_mult` resolver route through: `weapon_range <= 1` special-cases to the bare pre-existing `is_adjacent` check (no `has_los` test — melee never had one, and folding it into the general formula would let a diagonal-adjacent corner-wall case silently refuse a fight that used to connect); `weapon_range > 1` is `chebyshev <= weapon_range and has_los`. Byte-identical for every pre-GH#70 weapon (`sim_combat_batch.gd` proof). **Riposte gates on melee only** — `_resolve_hit`'s existing `melee` flag (physical-vs-magical math, not spatial) already excludes a bow's basic Attack from provoking counter_strike; a ranged hit still tallies `ranged_hit` unconditionally of that flag. Targeting UI (`targeting_controller.gd`'s Attack-slot candidate filter) widens/narrows the SAME distance check to the actor's own `weapon_range` instead of bare adjacency, `has_los` applied uniformly as before. Kit: `power_shot`/`quick_nock` reuse `damage_mult` verbatim (mult 2.0/0.7), `piercing_shot` reuses `line_damage` verbatim — zero new effect types. Earn: `ranged_hit` tallies on every landed hit from a `weapon_range > 1` combatant (`_resolve_hit`), OR banked directly by the barracks' `archery_butt` prop (item-gated on carrying any bow, `requires_weapon_family` — the #59 conversation item-gate's small parallel for a bare prop) — practice alone clears [Archer]'s `gained_by` threshold (3), no kill required, matching every other earned class's onboarding parity. `archer_earn_loop` = canonical proof.
  **Windup / telegraph mechanism (issue #82, boss design language):** `effect.windup_rounds` (only 1 supported) turns a skill into a two-beat DECLARE-then-RESOLVE: `use_skill` routes it to `WISkillEffects.declare_windup` instead of `resolve_active` — freezes the target cell set (blast/line derivation, `_radius_area` reused verbatim), spends the skill's own cost (a windup's `ap_cost` is typically the WHOLE turn — the "telegraphed AP spike"), emits `WINDUP_DECLARED {id, skill, cells}`, and deals NO damage yet. `WICombat.windups` (actor id -> `{skill_id, cells}`) parks the pending declare; `_start_turn` resolves it FIRST, at the caster's own next turn (`_resolve_windup`, the same multi-hit shape `blast_damage` uses but `melee=true` — STR-based, matching a physical attacker's own basic-Attack math, not blast_damage's INT-based spell default). **The caster is EXCLUDED from its own resolution, by id, never by cell** (F1 controller ruling): an adjacent range-1 declare geometrically always contains the caster's own cell and the melee AI never repositions after declaring, so caster-inclusion made every resolution a guaranteed self-hit — a tax, not a choice. Deliberate asymmetry vs player-cast `blast_damage`, which keeps caster-own-cell friendly fire as a chosen, card-warned risk; everyone ELSE in the frozen cells is still hit regardless of side. Counterplay is real, not flavor: whoever occupies the frozen cells AT RESOLUTION takes the hit, not whoever stood there at declaration — moving out whiffs it entirely. **Downed-clears is structural, not a special case**: `_advance_turn` already skips `_start_turn` for a dead combatant, so a caster killed before its next turn simply never resolves (no posthumous damage). `combat_ai.gd`'s melee profile gains ONE arm (`_windup_skill_id` + `windup_cadence`, a skill-level field): on a cadence round, adjacent, affordable — declare, ahead of the plain attack/power_strike branch. **[Dangersense]'s first real payoff**: the DECLARE's feed line + caster flash are universal (`WINDUP_DECLARED` rides `AI_PLAYBACK_TYPES` — the trap comment's own class, a mid-AI-turn event with a render arm); the frozen-cell board overlay (`board_renderer.gd`'s `add_terrain`/`expire_terrain` reused under a new `windup_danger` kind, PURELY presentation — no coupling to the sim's own `WICombat.terrain`) renders ONLY for a PC holding `dangersense` (`combat_playback.gd`'s enqueue-time `_pc_holds_dangersense` read), applied/cleared unconditionally outside `with_visuals` — the SAME "persistent state has no post-drain skip-resync" contract `TERRAIN_ADDED`/`TERRAIN_EXPIRED` established. Combat state (including `windups`) is NEVER save-serialized — verified (`WISave.serialize` has no `combat` field at all; a mid-fight save is structurally impossible), so no version bump was needed. First (and today only) holder: `slam` (`vault_construct`, the Guardian Construct boss, 8d C3) — `sim_combat_batch.gd`'s `vault_construct_t4_party` cell is GATED (0.55-0.95 win rate, 3-12 median rounds) against the real T4 Horns party.
  **AI profile variety (issue #83, gap-analysis: 28/33 combatants ran identical lowest-HP-melee AI):** three new `WICombatAI` profiles, all composed from EXISTING verbs (`attack`/`move_active`/`dash`/`use_skill` — no new effect types, no new `WICombat` state beyond the pure-derived `alive_allies_of`, the mirror of the pre-existing `alive_enemies_of`). **`skirmisher`** — attacks exactly like melee while it still has AP for another swing (STATELESS "already attacked" signal: `AP >= ATTACK_COST`, re-derived fresh every `_act_once` call, no new field), then spends leftover `move_pool` retreating from the nearest foe instead of standing in melee range. **`guard`** — when nothing is adjacent, its movement GOAL is its lowest-HP living ally's cell (`alive_allies_of`'s own hp-asc sort picks the ward), not the nearest/weakest enemy melee chases — body-blocks by positioning, not by any new redirect mechanic; once adjacent to a foe it fights exactly like melee (no windup arm — a future guard-profile windup holder needs the arm ported explicitly). **`coward`** — at/above `COWARD_FLEE_THRESHOLD` (0.3 of max_hp) is melee verbatim (including melee's own windup arm); below it, NEVER attacks: retreats from the nearest foe first, then (once no retreat step improves distance — cornered) rallies toward its NEAREST living ally instead (proximity-based, deliberately distinct from guard's HP-need-based pick). ## Working conventions

- Add ANY player-visible feature → extend QA script (or add new one in `qa/scripts/`) that walks it, asserts both domain event AND `ui_*_rendered` confirmation; run before claiming feature works.
- Content = data + code: new entities/skills in `data/*.json`; new behavior in sim; presentation only renders.
- Tests = plain SceneTree scripts under `tests/` (no GUT/gdUnit). Pure classes only — anything needing autoloads = QA-script territory.
- Balance changes = `combatants.json`/`skills.json` edits validated by `sim_combat_batch.gd` (GATED cells win-rate 0.55-0.95, median rounds 3-12; `goblin_ambush/warrior2` measured-only by user directive — see "Combat depth (M3)" block in `docs/ARCHITECTURE-HISTORY.md`) — never tune by feel. Combat data/rule change can invalidate canonical QA seed: re-verify `combat_walkthrough`/`level_up_loop`, update seed in this file's canonical seed table (and `qa/ci_sweep.sh`'s `CANON` array) if needed.
- GDQuest GDScript style: tabs, static typing, `class_name` + `##` doc comments.
- **Comment style (user directives 2026-07-07 + 2026-07-12, binds all new code + _comment fields):** comments state FUNCTION, CONSTRAINTS, TRAPS — never provenance — and are CAVEMAN-COMPRESSED: every comment earns its tokens (drop articles/filler/narrative; keep exact terms/ids/numbers; one compressed sentence of function + one of trap, max, for most JSON entities; state a trap ONCE at the seam and cross-reference by symbol, never per call site). Targets: .gd <= 20% comment lines, data <= 15% _comment chars (GH#102 tracks the census). No task/wave/review-finding narratives, no issue citations (exception: forward-promise to OPEN issue may cite it until issue closes). History lives in git blame, ledger, docs/ARCHITECTURE-HISTORY.md. Trap/contract comments (drift seams, order constraints, payload shapes) = the valuable kind — keep writing those. Legacy corpus thinned by GH#44 at 8a→8b boundary.

## Gotchas

- `CanvasLayer` has no `modulate` — tint/fade child Controls instead (exact bug shipped dead quest chain in v2).
- **Godot 4.7 `ResourceLoader.load()` returns NON-NULL but uncompilable script resource when .gd has parse/compile error** — null-checking load() not enough; load gate also checks `Script.can_instantiate()`.
- `--script`-mode runs don't resolve autoloads as bare identifiers — why purity rule exists; no autoload refs from `src/core/wi_game.gd`, `event_log.gd`, `qa_paths.gd`, or `tests/`.
- Commit generated `*.uid` sidecars alongside new `.gd` files.
- **Sprite frames with transparent padding below figure need measured `anchor`** (data/sprites.json). Feet-anchoring uses FRAME bottom — Body_A/Citizen_F's 16px under-feet padding (figure y 18–47 of 64) drew every character exactly ONE CELL above logical cell; player visually aligned with door/prop was physically row off, interact hit nothing. Fixed with `anchor: [0.5, 0.75]`. New character/prop sheet: measure figure bbox (PIL alpha scan), set anchor from FEET PLANE, not frame edge; verify with windowed adjacency screenshot.
- Web QA seeding (M3 T8): `run_web_qa.sh <script> <seed>` threads seed through `run_web_qa.mjs` -> `window.__WI_QA__ = {script, seed}` -> `game.gd._build_sim` reads via `JavaScriptBridge.eval(...)` only when `OS.has_feature("web")` AND no `--seed=` user arg given natively. Only `game.gd` reads *seed* off bridge (`qa/test_driver.gd` already uses `JavaScriptBridge.eval` for script-name/screenshot/result plumbing) — sim core in `src/core/**` never touches bridge, sim purity unaffected.
  Combat QA scripts now web-runnable (parity with native); `load_gate` stays native-only (see above).
- `WICombatAI.take_turn`'s `_act_once` defaults empty `"ai"` field (PC's own combatant config) to **melee** profile, which never inspects ranged/spell skills. So `combat_autoplay` NEVER casts spell for player character, any seed, any classes — `mage_unlock_loop` verifies mage kit via `combat.combatants.pc.max_mp` (nonzero only when known skill carries `mp_cost`), not observed cast.
